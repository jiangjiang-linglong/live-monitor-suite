## 二、Cookie 续期机制（你问的"能刷新的东西"）

**结论：小红书 cookie 里没有 OAuth 式 refresh token，能续期的就是 `web_session` 本身。**

- 实测业务接口（current_room_info / square_feed）的 Set-Cookie 只回 `acw_tc`（阿里 WAF 边缘 cookie，30 分钟、host-only、隔离在 `live-room.xiaohongshu.com` 域，不进共享 cookie），**`web_session` 不会在每次请求时轮换**。
- `web_session` 是服务端**滑动会话**：只要持续带 cookie 请求，服务端会不断续期，正常可维持数周~数月；长期闲置才会过期。
- 以前的问题：curl_cffi 响应里吸收的 cookie 只在内存，**从不回写 `login_cookies.txt`**，一旦服务端轮换了值、进程重启，就又用回旧值。

**现在的保障：**
1. pipeline 每 30 秒、watchdog 每 20 分钟探测后，把 cookie 原子回写 `login_cookies.txt`（仅 kv 集合变化时才写，临时文件 + replace，旧文件存 `login_cookies.bak`，自动剔除 `acw_tc`）。
2. 没有监控任务时，watchdog 每 20 分钟的探测请求本身就是**保活**，避免会话闲置过期。
3. 飞书妙记依赖的 lark-cli 登录态由其自身管理（`~/.lark-cli/` 加密存储，自带 refresh lock），不在本次范围内。

**唯一需要人工的情况：** 收到红色"登录态失效"卡片时，在 `Spider_XHS` 目录运行：

```bash
./.venv/bin/python do_login.py
```

扫码（可能登录码 + 风控码两步），覆盖 `login_cookies.txt` 后**无需重启**，守护探测到恢复会自动发绿卡。

## 三、每天怎么无人值守地跑

### 1. 服务常驻

```bash
# 查看状态
launchctl print gui/$(id -u)/com.causmatrix.xhs-watchdog | grep -E "state|pid"

# 手动重启
launchctl kickstart -k gui/$(id -u)/com.causmatrix.xhs-watchdog

# 停止 / 加载
launchctl bootout gui/$(id -u)/com.causmatrix.xhs-watchdog
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.causmatrix.xhs-watchdog.plist
```

### 2. 开播自动监控

- 守护每 60 秒检查目标房间；`status=2`（在播）→ 自动起 ffmpeg + pipeline（录像续段、弹幕/人数/商品采集、下播后自动交付），并发蓝色"自动开播"卡片。
- 下播后自动停止录制、不再重启；下一场开播自动再来。
- **room_id 每场直播会变。** 拿到新的分享链接后，只需改 `Spider_XHS/watchdog_config.json` 里的 `target.room_id` 一行，守护下一分钟自动生效；`host_id` 作为广场兜底匹配。

### 3. 录像生命周期

- 视频文件（`.ts/.mp4`）**保留 24 小时后自动删除**（今天已按此执行）。
- **CSV / 报告 / 逐字稿 / 音频（.m4a）永久保留**，不在清理范围。
- 正在录制的目录按 ffmpeg 进程精确保护，且 15 分钟内写入过的文件绝不删，双保险。
- 磁盘告急时按 92% 应急策略先删最旧的非录制视频。

### 4. 手动提前截止并交付

直播还没下播但要提前收尾时，先在 `watchdog_config.json` 把 `target.room_id` 清空（防止守护重启该房间），
停掉对应 ffmpeg/pipeline，然后运行 `cut_deliver.py`（参数与 pipeline 完全一致），它会从
`signal_state.json` 恢复全部已采集信号，执行与正常下播完全相同的交付：

```bash
cd Spider_XHS
./.venv/bin/python cut_deliver.py <room_id> <host_id> <主播名> <输出目录> <webhook> <chat_id> <lark_cli>
```

### 5. 告警卡片说明

| 颜色 | 含义 | 你需要做什么 |
|---|---|---|
| 蓝 | 启动/自动开播/清理完成等例行通知 | 无需处理 |
| 黄 | 磁盘 80%、接口疑似异常（连续 6 次） | 留意即可 |
| 红 | 登录态失效、风控、磁盘 90%/92%、relay/会话启动失败、WS 信号中断 | 红卡正文会写清处置步骤；登录态按第二节扫码 |
| 绿 | 故障恢复 | 无需处理 |

同故障按 key 去重限时重发，不会刷屏；升级立即发。

### 6. 交付内容（2026-10-27 按客户沟通调整）

- **商品款式图**：多维表「商品讲解 / 商品热度榜 / 爆品时刻」三张表均有「商品图」附件列（商品卡官方图，非直播截图）；

## 七、看板切片器与口径说明

### 1. 两个全局切片器

看板顶部配置了两个筛选器，联动看板上**全部图表**：

| 切片器 | 选项 | 作用 |
|---|---|---|
| **主播筛选** | 全部 / XIAOQSTUDIO / 张大奕eve / …（按实际出现的主播自动列出） | 按主播过滤场次表与 6 张明细子表 |
| **场次筛选** | 全部 / 各场直播场次名 | 按单场直播过滤 |

实现要点：7 个数据源（场次表 + 在线人数/互动明细/爆品时刻/商品讲解/商品热度榜/话术词 6 张子表）都已映射「主播名」「场次名称」两个文本字段。
**这两个字段在每场直播结束时由 pipeline 自动写入**，无需手工维护；历史缺数据的场次可用 `backfill_slicer_fields.py` 回填：

```bash
cd monitor   # 开发机上为 Spider_XHS
./.venv/bin/python backfill_slicer_fields.py <场次record_id> <主播名> <场次名称>
```

> 多数据源切片器只能在飞书多维表格浏览器界面里配置，开放 API 不支持配置/修改；已在 UI 完成并实测联动。

### 2. 看板上的「口径说明」文本块

口径说明固定在看板左上角，与图表同步显示，内容：

- 在线人数：每 5 秒轮询直播间公开数据，峰值/均值按明细最大值/平均值计算
- 爆品时刻：在线人数较基线突增，且当时命中商品讲解
- 去买次数：观众点击商品卡/购买按钮的次数，非真实销量
- 商品热度榜：热度分 = 购买信号×10 + 相关弹幕×3 + 讲解时长×0.1 + 讲解次数×2
- 切片器：上方主播/场次筛选联动本看板全部图表

> 已知坑：多维表文本块经开放 API/CLI 修改会双重编码（内容被存成带引号的 JSON 字面量），文本块只能在浏览器 UI 编辑。

## 八、部署到客户电脑（live-monitor 部署包）

代码已整理为自包含 git 仓库（`live-monitor`），客户机为 macOS 时：

```bash
git clone https://gitee.com/michael_1226/live-monitor.git
cd live-monitor
bash xhs/deploy/install.sh
```

install.sh 自动完成：检查并用 Homebrew 安装 node/ffmpeg → 创建 Python 虚拟环境并装依赖 → 生成 `feishu/feishu_app.json` 模板（填 app_id/app_secret/base_token 后重跑）→ 引导小红书扫码登录 → 自检一轮 → 安装 launchd 常驻。

部署后只需在 `monitor/watchdog_config.json` 填 `target.host_id`（或 `target.room_id`）。

**注意：**
- 妙记转写依赖 lark-cli 登录态（豆包环境内置）；客户机没有 lark-cli 时，其余交付（多维表、CSV、报告、人数曲线、群卡片、商品图）全部正常，仅整场逐字稿/音频转写自动跳过。
- 仓库不含 `feishu/feishu_app.json`、`login_cookies.txt`（.gitignore 已排除），换机时各自重新生成。
